Data Flow: Lesson Completion

Step Action System
1 User clicks "Complete Lesson" Frontend
2 Save completion to MySQL Main App
3 POST /webhook/lesson-complete Main App → Progression
4 Verify API key, find/create user Progression Service
5 Add +50 XP, check for level-up Progression Service
6 Return updated stats Progression → Main App
7 Display level-up animation Frontend

Key Point

The main app does not wait for the webhook response to show "Lesson Complete" to the user. The webhook is fire-and-forget — the XP update happens asynchronously.

Authentication: Two Methods

🔐 JWT (User Routes)

Used for:

  • GET /users/me
  • POST /users/me/lessons/complete
  • POST /users/me/quizzes/submit
Header: Authorization: Bearer <token> // Token expires in 7 days // Generated via POST /auth/login

Purpose: Identify who is making the request (the user)

🔑 API Key (Webhooks)

Used for:

  • POST /webhook/lesson-complete
  • POST /webhook/quiz-submit
  • GET /users/:userId
Header: x-api-key: main-system-integration-key // Shared secret between services

Purpose: Identify which service is calling (main app)

Challenges & Solutions

❌ CORS Errors

Problem: Browser blocked requests from main app to progression service

Solution: Added cors() middleware

❌ Two Auth Systems

Problem: Needed JWT for users + API Key for services

Solution: Implemented separate middleware functions

❌ In-Memory Persistence

Problem: Data resets when server restarts (Render free tier)

Solution: Documented limitation; acceptable for academic demo. Future: Redis/PostgreSQL

❌ XP Calculation Edge Cases

Problem: Exponential scaling caused multi-level jump issues

Solution: Implemented while-loop for accurate multi-level progression

❌ Render Cold Starts

Problem: Server takes time to wake up after inactivity

Solution: Added health check endpoint; ping before demo

❌ Data Format Consistency

Problem: Different user ID formats between services

Solution: Standardized on string-based userId across both
